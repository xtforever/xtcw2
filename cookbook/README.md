# cookbook — reference xtcw2 application

A small "cookbook" (recipe manager) demo application whose job is **not** to be a
polished product, but to be a realistic, buildable and deployable example of how
a project is structured with **xtcw2**. It is used to exercise the whole toolkit
end-to-end (build system, widgets, LUI, themes, the `commander_runner` host, and
the deployment path) and to drive [`../plan-xtcw-completed.md`](../plan-xtcw-completed.md).

The app is intentionally a reference skeleton: some screens are wired only far
enough to build, render and start. That is enough to catch build/runtime
regressions across the toolkit.

## What it demonstrates

- A **LUI/Lua** application loaded by `commander/commander_runner` (the xtcw2
  host), with a multi-screen structure and a small data model.
- Use of a wide slice of the widget set: labels, buttons, lists, edits,
  spinboxes, combos, checkboxes/radios, multi-line editors, menus and dialogs.
- Theming via the central theme registry.
- A **debug and a production** build (production = `-O3`, no `-DMLS_DEBUG`, no
  AddressSanitizer) plus a headless **start smoke test** under Xvfb.
- A **Docker** build/packaging story for deployment.

│   │   ├── recipe_detail.lua
│   │   ├── recipe_editor.lua

`dist/` (generated by `scripts/test-all.sh`) is not committed.

## Prerequisites

Build toolchain:

- `gcc`, `make`, `pkg-config`, `bison`, `flex`, **`swig`**
- X11 / Xt / Xaw / Xmu / Xft / Xpm / Xext / Xrender / fontconfig dev libraries
- `cairo` (incl. `cairo-xlib`)
- `lua5.3` development package and the Lua `lpeg` module
  (Debian/Ubuntu: `liblua5.3-dev lua5.3 lua-lpeg`)

The `LuaRunner/nanosvg` subtree is a **git submodule** — initialise it once:

```bash
git submodule update --init --recursive
```

For the smoke test and full regression:

- `xvfb` (headless X server) and `x11-utils` (for `xwininfo`)
- optionally `scrot`, `python3-pil`, `python3-numpy` (only for the repository's
  own `commander/run_demo_tests.sh`)

## Building

> **Always build from the repository root.** The toolkit libraries and
> `commander_runner` must agree on the `MLS_DEBUG` setting; mixing debug and
> non-debug objects crashes at runtime. Building a sub-make directly bypasses the
> root mode switch.

```bash
# from the repository root
./cookbook/scripts/build.sh debug        # debug:  -g -O0 -DMLS_DEBUG -fsanitize=address
./cookbook/scripts/build.sh production   # release: -O3, no MLS_DEBUG, no ASan
```

Each invocation runs `make distclean` first, so switching modes is always clean.
The result is `commander/commander_runner` in the requested mode.

## Running

```bash
./cookbook/scripts/run.sh
```

This runs `commander_runner` from `commander/` (the host requires this working
directory for its relative `../lui/?.lua` path) with the cookbook entry script
and theme. With no `DISPLAY`, use `xvfb-run -a ./cookbook/scripts/run.sh`.

## Testing

```bash
./cookbook/scripts/smoke-test.sh debug        # start smoke test, debug binary
./cookbook/scripts/smoke-test.sh production   # start smoke test, production binary
./cookbook/scripts/test-all.sh                # both modes; archives to dist/<mode>/
```

`smoke-test.sh` starts a headless X server, launches the app, and checks that a
window appears and that no fatal error was logged. The app is only required to
*start and render*, not to be fully functional.

## Docker

The build context must be the **repository root** (the whole toolkit is needed),
and the `LuaRunner/nanosvg` submodule must already be checked out on the host
(`git submodule update --init --recursive`).

```bash
# from the repository root
docker build -f cookbook/Dockerfile --target debug      -t xtcw-cookbook:debug      .
docker build -f cookbook/Dockerfile --target production -t xtcw-cookbook:production .
```

Each target compiles xtcw2 in the requested mode and runs the corresponding start
smoke test. The production image is the deployable artifact; the debug image uses
AddressSanitizer.

Run one of them (the container starts its own Xvfb):

```bash
docker compose -f cookbook/docker-compose.yml run --rm production
docker compose -f cookbook/docker-compose.yml run --rm debug
```

The debug service runs with `security_opt: seccomp=unconfined` and `setarch -R`
because AddressSanitizer needs to control the address-space layout. The
`cookbook/Dockerfile.dockerignore` keeps generated objects/archives and the
`.git`/`experimental` trees out of the build context.
